# docs — ドキュメンテーション

`plan` の「ドキュメント版」。あらゆる Markdown ドキュメントを、**過不足なく・構造化され・人にも AI にも読みやすい**形で作る/整える。実装とドキュメントを同期させる用途も含む（後述）。

## 原則

- **過不足なく**: 目的に必要な情報だけを、漏れなく書く。冗長・重複・空セクションを作らない。
- **構造化**: 見出し階層・箇条書き・表・コードブロック・Mermaid を使い、走査しやすくする。
- **人にも AI にも読みやすい**: 用語を統一し、結論を先に、前提・理由を添える。曖昧表現を避ける。
- **推測で埋めない**: 不明点は書き始める前にユーザーへ質問して埋める。

## 対象

- `docs/` 配下（要件定義 / アーキテクチャ / ディレクトリ構成 / DB 設計 / 機能仕様 / 画面別解説 など）
- `README.md`
- その他、リポジトリ内外の任意の Markdown（設計メモ、調査メモ、手順書、提案書 など）
- 図は `docs/img/` を活用し、構造図・フローは Mermaid を積極的に使う。

## 手順（作成・編集）

1. **概要の受け取り**: 起動時の引数で「何のドキュメントか」の概要を受け取る。引数がなければユーザーに概要を尋ねる。
2. **目的の明確化**: そのドキュメントの **目的**（何のために・何を達成したいか）と **対象読者**（新規開発者 / 利用者 / 自分の備忘 / AI など）を確定する。目的が曖昧なら確認する。
3. **不足情報の深掘り（質問）**: 目的に対して内容が不足している場合、`AskUserQuestion` 等でユーザーに **質問を重ねて回答を深掘り** する。必要な情報（背景・前提・スコープ・具体例・制約・期待する粒度など）が揃うまで本文を書き始めない。
4. **構造設計**: 集めた情報から、見出し構成（アウトライン）を先に設計する。過不足がないか目的と照合する。必要に応じてアウトライン段階でユーザーに確認する。
5. **執筆/編集**: アウトラインに沿って書く。結論先行、用語統一、表・コードブロック・Mermaid を適切に使う。FSD のレイヤー/スライス名など、プロジェクト用語は実装・`CLAUDE.md` と統一する。
6. **整合チェック**: 既存ドキュメントや `CLAUDE.md` と矛盾しないか確認する。記述の「正」は to-be 設計（再開発方針）に合わせる。
7. **報告**: 作成/更新したファイルパスと、構成・主要ポイントを要約して返す。

## 手順（実装変更後の同期）

実装とドキュメントを揃える側面。`feat:` / `refactor:` を伴う変更の後、または明示指示があったとき:

1. `src/` 配下（app/pages/widgets/features/entities/shared）の変更を走査する。
   - 各スライス `index.ts` の公開要素の増減、Props/状態の変更、ロジックの意図（JSDoc・教育的配慮コメント）。
2. 該当するドキュメント（機能仕様 / ディレクトリ構成 / shared/lib のユーティリティ等）を更新する。
3. 実装にあるが未記載の Public API、削除済みなのに残っている記述がないか確認する。
4. 更新したファイルパスと「実装に合わせて更新した主要項目」を要約して報告する。

## 注意

- 実装提案時にドキュメント更新が必要だと判断したら、その旨を併せて提案する。
- ドキュメント変更のコミットは `docs:` type（`commit` スキル参照）。
