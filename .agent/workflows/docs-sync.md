## 1. コードベースの全域走査

単なるファイル名だけでなく、以下の観点で `src/` 配下の全レイヤー（app, pages, widgets, features, entities, shared）を分析します。

* **Public API の変更**: 各スライスの `index.ts` から export されている関数、型、コンポーネントの増減。
* **Props/State の変更**: 3Dモデル（Robot等）の制御用 Props や、グローバルな状態（Zustand等）の定義変更。
* **ロジックの意図**: コード内の JSDoc や「教育的配慮コメント」から、数式やアルゴリズムの解説箇所を抽出。

## 2. ドキュメントの更新・生成

走査結果に基づき、以下のファイルを更新します。

* **ページ別解説 (`docs/pages/*.md`)**:
* 画面構成（どの widget を配置しているか）の更新。
* 新しく追加された操作フロー（例：ARモードでのQRスキャン手順）の追記。


* **ディレクトリ構造 (`docs/directory-structure.md`)**:
* `tree` コマンド相当の構造を再生成。
* 新しく作成されたスライスやセグメントに簡潔な説明を付与。


* **技術スタック/APIリファレンス**:
* `shared/lib` に追加された数学ユーティリティ等のドキュメント化。



### 3. 整合性チェック

更新後、以下の矛盾がないか最終確認を行います。

* 実装コードには存在するが、ドキュメントに記載がない Public API はないか。
* すでに削除されたファイルや機能が、ドキュメント内に残っていないか。

### 4. 実行タイミングと報告

* **タイミング**: `feat:` や `refactor:` を含むコミットの直前、またはユーザーからの明示的な指示があった時。
* **報告形式**:
* 修正したドキュメントのファイルパス。
* 「実装に合わせて更新した主要な項目」の要約。



**エージェントへの指示**:
実装を提案する際、もしドキュメントの更新が必要だと判断した場合は、実装コードの提示と同時に「ドキュメント同期ワークフローの実行」を提案してください。
