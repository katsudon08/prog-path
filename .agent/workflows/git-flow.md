## 1. 変更内容の事前検証

コミットを行う前に、以下の確認を行います。

* **差分分析**: `git diff` を実行し、コードの変更が `01-architecture.md` および `02-coding.md` に準拠しているか再確認する。
* **不要ファイルの混入チェック**: 一時ファイル、デバッグ用の `console.log`、および `.gitignore` に含まれていない不要なアセットが含まれていないか確認する。

## 2. コミットメッセージの生成（Conventional Commits）

以下の形式でメッセージを作成します。

`type(scope): title`

`description`

* **type**:
* `feat`: 新機能（FSDのスライス追加など）
* `fix`: バグ修正
* `docs`: ドキュメント作成・修正
* `style`: コードスタイルのみの修正（見た目、整形）
* `refactor`: 機能変更を伴わないコード整理
* `perf`: パフォーマンス改善
* `chore`: ビルド設定やライブラリの更新


* **scope**: 変更を加えた FSD レイヤーまたはスライス名（例: `shared/ui`, `entities/robot`, `pages/maze`）。
* **title**: 命令形ではなく、何をしたかを日本語で簡潔に記述。
* **description**: どのようなことをしたのかを日本語で少し詳細に記述。

## 3. 実行フロー

1. **ブランチ確認**:
* `git branch --show-current` を実行。
* **`main` ブランチの場合**: 直接の操作を中断し、作業用ブランチ（例: `feat/...`）への切り替えを促す。


2. **ユーザー確認**:
* 生成したメッセージと変更ファイル一覧を提示し、「コミットおよびプッシュを実行しますか？」と確認を求める。


3. **実行コマンド（承認後）**:
* `git add .`
* `git commit -m "[生成したメッセージ]"`
* `git pull --rebase origin [ブランチ名]` （競合の事前防止）
* `git push origin [ブランチ名]`



## エージェントへの指示

* プッシュに失敗した場合（権限エラーや競合など）は、エラー内容を分析してユーザーに次のステップ（手動での解決方法など）を仰いでください。
* 大規模な変更（多数のファイルにわたる場合）は、一つのコミットにまとめず、機能単位で分割してコミットすることを提案してください。
