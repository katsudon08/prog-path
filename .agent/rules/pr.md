# Pull Request Convention

AI がプルリクエストを作成する際のフォーマットとルールを定義します。

---

## タイトルフォーマット

```
[type] #<issue-number> subject
```

- `[type]` は角括弧付きで先頭に記載（issue.md の type と統一）
- `#<issue-number>` は紐づく Issue 番号（必須。Issue がない場合は省略可）
- subject は日本語・体言止めまたは「〜を追加/修正/削除」形式
- 全体で 72 文字以内

**例:**
```
[feat] #123 ユーザープロフィール画像のアップロード機能を追加
[fix] #456 ログイン後のリダイレクト失敗を修正
[chore] #789 ESLint を v9 に移行
[docs] API 認証フローのドキュメントを追加
```

---

## Type 一覧

commit.md / issue.md と統一します。

| type | 用途 |
|------|------|
| `feat` | 新機能 |
| `fix` | バグ修正 |
| `refactor` | リファクタリング |
| `docs` | ドキュメント |
| `chore` | 環境整備・依存更新 |
| `test` | テスト追加・修正 |
| `spike` | 技術調査・PoC |
| `hotfix` | 本番緊急修正 |

---

## PR テンプレート

```markdown
## 概要
<!-- このPRで何をしたか・なぜしたかを2〜3文で -->

## 変更内容
- [ ] 変更点 1
- [ ] 変更点 2

## 関連 Issue
Closes #[番号]

## 動作確認
- [ ] ローカルで動作確認済み
- [ ] 主要なケースを手動テスト済み

## スクリーンショット（UI変更がある場合）
| Before | After |
|--------|-------|
|        |       |

## レビュー観点（任意）
<!-- レビュアーに特に見てほしい箇所や懸念点があれば記載 -->

## 補足（任意）
<!-- 設計上の判断理由・既知の制限・今後の課題など -->
```

---

## ラベル運用

issue.md のラベルと対応させます。

| ラベル | 意味 |
|--------|------|
| `type: feat` | 新機能 |
| `type: fix` | バグ修正 |
| `type: chore` | 雑務・環境 |
| `type: hotfix` | 本番緊急修正 |
| `priority: high` | 優先度高 |
| `status: in-progress` | 作業中（Draft PR） |
| `status: ready` | レビュー依頼可能 |
| `needs: review` | レビュー待ち |

---

## Draft / Ready ルール

| 状態 | 条件 |
|------|------|
| **Draft PR** | 作業中・WIP・レビュー不要の段階。タイトル冒頭に `[WIP]` は不要（GitHub の Draft 機能を使う） |
| **Ready for Review** | 動作確認済み・セルフレビュー済み・CI グリーンの状態でのみ Ready に変更する |

---

## マージ戦略

| マージ先 | 方法 | 理由 |
|---------|------|------|
| `develop` | **Squash merge** | 機能単位でコミット履歴を整理する |
| `main` | **Merge commit** | `develop` → `main` のリリース履歴を残す |

---

## レビュー完了条件

- [ ] Approve が最低 1 件ついている
- [ ] CI（lint / test / build）がすべてグリーン
- [ ] 指摘コメントがすべて Resolved または返答済み
- [ ] コンフリクトが解消されている

---

## AI への指示テンプレート

```
以下の情報をもとに、pr.md のルールに従ってプルリクエストのタイトルと本文を生成してください。

## 作業内容
[実装・修正の内容を自由記述]

## 関連 Issue 番号
#[番号]（なければ「なし」）

## UI 変更の有無
あり / なし

## 制約
- タイトルは [type] #番号 subject 形式・日本語・72文字以内
- テンプレートのすべてのセクションを埋める
- 動作確認項目は作業内容に合わせて具体化する
- レビュー観点には実装上の判断や懸念点を含める
```
