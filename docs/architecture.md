# 概要

このファイルは、ProgPathの設計を実装のレベルに落とし込み、それをアーキテクチャの概念についても詳細に記載するファイルである。

## 採用の背景

本プロジェクトProgPathは、迷路・コマンド・ロボットなどのドメインに近い要素を頻繁に扱うため、Componentベースの設計（`Component`ディレクトリで切り分ける手法）ではドメイン関連がどんどん複雑になり、新規機能の追加や機能修正が困難になる可能性があるため、ドメインを切り離し、レイヤーごとに管理することができるFSDアーキテクチャを採用することにした。

## アーキテクチャのルール

本アプリにおいて使用するアーキテクチャは、**FSD**(Feature Sliced Design)を使用する。

### レイヤー

構成としては、以下の**レイヤー**によって構成される。

```
src
├─ app
├─ pages
├─ widgets
├─ features
├─ entities
└─ shared
```

それぞれのレイヤーについての説明を行う

**app**：アプリ全体の設定やスタイル、プロバイダーなどを配置する

**pages**：各ページのレイアウトを構成する

**widgets**：featuresやentitiesを組み合わせて、画面の中に存在する大きめな部品をつくる

**features**：ユーザーが行う行動をまとめて、機能ごとに切り分ける

**entities**：ビジネスロジックにおけるデータ構造とそれに関する表示やルールなどを配置

**shared**：共通のUIや関数などを配置する

また、レイヤーにおいて下記の向きの一方向のみの依存しか許されず、下位のレイヤーから上位のレイヤーへの依存は許可されない。
（同じレイヤー間でも同様）

例としては、`entities`が`features`を参照したり、`features/A`が`features/B`を参照するなどがあってはいけない。
（スライスはそれ単体で完結するべきだから）

以下はその方向を示したものである。

```
app > pages > widgets > features > entities > shared
```

### スライス

また、それぞれのレイヤーは**スライス**という単位によってさらに切り分けることができる。

これはビジネスロジックを単位に切り分ける。

例として、以下のようになる。

```
features
├─ auth-by-phone
└─ inline-post
```

また、先ほども軽く触れたが同じレイヤーのスライス間では依存が禁止されている。

これには循環依存を防ぐほか、コードの関係が不透明になったり機能ごとにきちんとスライスを分けることを目的としている。

ただし、**app**と**shared**レイヤーにおいてはビジネスロジックによる分割はプロジェクト全体で使いまわすため、不要なので行わず、直接**セグメント**により切り分けます。

### セグメント

各スライスは**セグメント**という単位でさらに切り分ける。
これは基本的自由に追加することができると公式で名言されているが、基本的には以下のものを使用するようにする。

```
{layers}
└─ {slices}
   ├─ ui
   ├─ model
   ├─ lib
   ├─ api*
   └─ config*
```

`*`がついている**api**と**config**については、使う必要はない。

また、セグメントでは技術的単位で切り分ける。

### Public API

各スライスは、そのスライス自体の境界線を示すことを目的とするために`index.ts`を配置し、それをバレルファイルとしてまとめて中にある関数や変数などを公開する。

これにより、他のレイヤーからそのスライスの機能を参照したいとき、中のどこに書いてあるかを気にすることなく用いることができる。

また、`shared`レイヤーにおいてのみ特別にセグメントの中に直接`index.ts`を配置することで、それぞれの機能の**境界線**の役割を担う。

### スライス・セグメントにおける分割

スライスやセグメントはそれぞれネストすることはないが、中でどうしても複雑になってきたり、ファイル数が多くなってきてしまったときは、ディレクトリで分割してもよい。

ただし、ディレクトリ分割はあくまでも**ファイル整理**の目的で行うものであり、境界線を設けるものではないため、`public API`を定義する`index.ts`では、分割されたディレクトリ内のファイルをすべて参照する必要がある。
