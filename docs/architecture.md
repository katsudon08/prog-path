# アーキテクチャ方針（Architecture）

本プロジェクトでは、コードベースの保守性、予測可能性、再利用性を極大化するために **[Feature-Sliced Design (FSD)](https://feature-sliced.design/)** アーキテクチャを採用しています。

FSDは、アプリケーションを主に「Layer (レイヤー)」「Slice (スライス)」「Segment (セグメント)」という直交した3つの概念で分割します。

## 1. Layers（レイヤー）
システム全体の階層ごとの責務を定義します。**「上位レイヤーは下位レイヤーをインポートできるが、その逆は禁止する（単方向の依存関係）」** という絶対ルールがあります。

上から下への順序は以下の通りです：

1. **`app/`**: アプリケーションのエントリーポイント
   - 全体設定、グローバルプロバイダ、ルーティングの設定などを行います。
2. **`pages/`**: 画面（ページ）
   - 下位レイヤーのコンポーネント（WidgetsやFeatures）を組み合わせて、1つのURL・画面を構築します。
3. **`widgets/`**: 独立した複合機能ブロック
   - 複数のFeatureやEntityをまとめた独立性の高いコンポーネントです。（例: `camera-scanner`, `simulation-board`）
4. **`features/`**: ユーザーストーリー・ドメインの中核機能
   - ユーザーのユースケースをもたらす機能単位です。（例: `scan-qr-command`, `control-robot`）
5. **`entities/`**: ビジネスエンティティ（コア概念）
   - ビジネスドメインの中核となる概念や型、それらを表現する純粋なUI部品です。（例: `robot`, `command`, `maze`）
6. **`shared/`**: 共有・汎用要素
   - ドメイン（ビジネス）知識を一切持たない領域です。汎用UI（ボタン、UIキット）、共通ユーティリティ（APIクライアント、設定情報）がここに入ります。

## 2. Slices（スライス）
各レイヤー（`app`と`shared`を除く）内部を、特定のドメイン単位で切り分けたディレクトリです。
- 例えば `entities` レイヤーの中に `entities/robot/` や `entities/command/` といったスライスが存在します。
- **重要**: スライスをまたいだ直接的なインポート（クロスインポート）は原則禁止です（例えば `entities/robot` が `entities/command` を直接インポートしてはいけません）。これによりドメインごとの高い独立性を保ちます。
- **Public APIの強制**: スライスの外（別のレイヤーなど）に機能を公開する場合は、必ず各スライスのルートにある `index.ts`（Public API）のみを使用します。スライス内の特定ファイルへのディープインポートは禁止です。

## 3. Segments（セグメント）
各スライスの内部を、技術的な役割ごとに切り分けたディレクトリ（あるいはファイル）です。標準的なセグメントには以下が含まれます：
- **`ui/`**: 画面に描画されるReactコンポーネント（例: `robot-card.tsx`）。
- **`model/`**: ビジネスロジック、状態管理（Hooks、Storeなど）。
- **`lib/`**: スライス専用のヘルパー関数やユーティリティ。
- **`api/`**: 外部との通信処理（APIリクエスト等）。

### スライスの構成例
Entitiesレイヤーにおける `robot` スライスの構成例です：
```text
src/
└── entities/
    └── robot/             # ⬅ これがSlice（スライス）
        ├── index.ts       # ⬅ Public API（ここから外部へ公開）
        ├── ui/            # ⬅ 以下 Segments（セグメント）
        │   └── robot-avatar.tsx
        ├── model/
        │   ├── types.ts
        │   └── use-robot-state.ts
        └── lib/
            └── calculate-position.ts
```

## FSDのメリット
- **予測可能性の向上**: コードがどこに置かれているか（ドメインによるSliceか、技術的役割のSegmentか、抽象度によるLayerか）が明確になります。
- **リファクタリングの安全性**: 一方向の依存関係とPublic APIの制限により、あるSliceの内部実装を変えても、他のSliceや上位Layerに影響が波及しにくくなります。
