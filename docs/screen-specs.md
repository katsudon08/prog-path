## 1. このドキュメントの位置づけ

### 1.1 なぜ必要か

`features.md` は「QR を読むと命令が追加される」までは決めているが、**その命令行が何 px で、何件見えるか**は決めていない。この層が空白のまま widgets を実装すると、画面ごとに寸法がばらつき、後から全画面を作り直すことになる。

とくに本アプリは **囲んで見る外側の子に届く文字サイズ**が成立条件そのものなので、寸法は「見た目の好み」ではなく**要件**である（→ 2.2）。

### 1.2 対象読者

各画面を実装する開発者。実装前にその画面の章だけを読めば、寸法・配置・要素数が決まる状態にする。

## 2. 共通の土台

### 2.1 設計基準ビューポート — 1280 × 600 CSS px

文科省の GIGA スペック基準に**解像度の規定はない**（「画面 10〜14 インチ、タッチパネル」のみ）ため、実機から逆算する。

| 区分 | 値 | 根拠 |
| --- | --- | --- |
| **設計基準（Web / Tauri 共通）** | **1280 × 600** | 幅 = 10.1 インチ機（1280×800）／高さ = 下記の控除計算 |
| Tauri 実効（装飾あり・最大化） | 1280 × 680 | 768 − 48（タスクバー）− 32（タイトルバー） |
| **劣化フロア**（保証しないが破綻させない） | **1024 × 450** | 1366×768 を 125% スケーリングした場合 |

**高さの控除**（Chromium `layout_constants.cc` の実定数から導出）

```
768（11.6 インチ機の物理解像度・表示スケール 100%）
 − 48   Windows 11 タスクバー
 − 115  Chrome / Edge の UI（タブ帯 41 + ツールバー 40 + ブックマークバー 34）
 ─────
 = 605  → 切り下げて 600 を設計基準とする
```

- 11.6 インチ帯（GIGA の主力）は例外なく 1366×768、最小幅は 10.1 インチの 1280。
- StatCounter で `1366×768` が生の CSS 解像度として観測される（日本 4.36% / 2026-07）ことが、**それらの端末が表示スケール 100% で動いている証拠**になる。`screen.width` は CSS px を返すため、125% なら `1092×614` が現れるはずだが存在しない。
- **Tauri のほうが 80px 高いが、2 種類のレイアウトを保守しない。** 1280×600 に一本化し、余剰は「セルが大きくなる」形で自然に吸収させる。

> **Tauri 側の必須設定**: `WindowConfig` の既定は `800×600` / `maximized: false` / `zoomHotkeysEnabled: false`。**すべて明示指定が必要**。とくに `zoomHotkeysEnabled: false` のままだと Ctrl +/− が効かず、**Tauri 版だけ WCAG 1.4.4（Resize text）を落とす**。

### 2.2 タイポグラフィ階層

**囲んだノート PC は 10-foot UI である。** 視角計算（ISO 9241-303: 最低 16 分角 / 推奨 20〜22 分角）で検証した。

| 状況 | 画面が視野に占める水平角 |
| --- | --- |
| 13.3" を 40cm から（1 人で操作） | 40.4° |
| **14" を 70cm から（囲む 3 人目）** | **25.0°** |
| **55" TV を 3.05m から（10-foot UI の想定）** | **22.6°** |
| **11.6" を 70cm から** | **20.8°** |

> 囲んでいる外側の子が見ている画角は、リビングの 55 型 TV を 3m から見るのとほぼ同じ。したがって 3-foot UI（デスクトップ）ではなく **10-foot UI の設計則**で作る。

**確定スケール**（画素ピッチ 0.18mm/CSS px、cap height 0.72em で算出）

| 用途 | サイズ | ISO 16′ を満たす視距離 | 例 |
| --- | --- | --- | --- |
| 補助情報 | **18px** | 501mm | メタ情報・要件・非アクティブ行 |
| **本文** | **22px** | 613mm | 説明文・迷路名・命令チップ |
| **主要ラベル** | **30px** | 836mm | ボタン文言・見出し・ページ名 |
| **状態表示** | **36px** | 1003mm | 移動カウント・実行中の値 |
| 禁止 | **16px 未満** | — | バッジ・キャプションも例外にしない |

- 画面高比で独立に計算しても同じ結論になる（Microsoft の 10-foot 規定 15epx/540epx = 画面高 2.78% → 768px なら 21.5px、主要ラベル 4.0% → 30.7px）。**2 つの独立した手法が 20〜31px で一致**する。
- **斜めから見る子への配慮**: 横から覗く子は距離が伸びるうえ画面が斜めに縮み、**画面の遠い端に置いた文字は実効 12〜24% 小さくなる**（15.6" で 76%、11.6" で 88%）。ただし**縦方向には縮まない**。→ **情報は横に広げるより縦に積む。左右端の各 5%（各 64px）には操作対象・テキストを置かない。**

**WCAG の "large text" 境界に注意**

WCAG 1.4.3 の "large text" は **24px（regular）/ 18.66px（bold）以上**。

| サイズ | large text か | 必要コントラスト | 影響 |
| --- | --- | --- | --- |
| 18px regular | ✗ | 4.5:1 | `muted-foreground`（5.22 / 7.64）は OK |
| 22px regular | ✗ | 4.5:1 | **ソリッド面に載せられない**（`primary` / 白 = 3.26） |
| **22px bold** | **✓** | 3:1 | **ソリッド面に載せられる** |
| 30px / 36px | ✓ | 3:1 | 問題なし |

→ **ソリッド面に載る 22px は必ず bold にする**（コマンドチップ・タイルラベル等）。BIZ UDPGothic は 400 / 700 の 2 ウェイトなので 700 を使う。

### 2.3 タップターゲットと Button スケール

**文字は上げるが、ターゲットサイズは上げない。** 可読性（文字サイズ）とターゲットサイズは別問題であり、ProgPath は**マウス主体**（タッチ併用）かつ対象年齢 10〜12 歳は運動能力がほぼ成人並みのため、48px で足りる。

| size | 高さ | 文字 | 用途 |
| --- | --- | --- | --- |
| `sm` | **48px** | 18px | 補助操作 |
| `md` | **56px** | 22px | 標準 |
| `lg` | **72px** | 30px | 主役（`▶ うごかす` / `ほぞんして とじる`） |

- 現行の `sm`=44 / `md`=48 / `lg`=56 は 14/16/18px 前提であり、新スケールでは文字が入らない。**改訂が必要**（→ 8.2）。
- `--spacing-tap-min`(44) / `tap`(48) / `tap-lg`(56) はそのまま使え、**72px 用に `--spacing-tap-xl: 4.5rem` を追加する**。
- **操作可能要素の下限は 48px を維持**（WCAG 2.2 SC 2.5.8 の 24px を大きく上回る安全側）。

### 2.4 レイアウトの基本則

| 項目 | 規定 |
| --- | --- |
| ルート | `h-dvh`（`min-h-dvh` ではない）+ `overflow-hidden`。スクロールを許す領域を**明示指定**する |
| navbar | **72px 固定**。全画面で位置・高さを変えない（AR 実行のみ非表示） |
| 左右端 5%（各 64px） | 操作対象・テキストを置かない（斜め視の縮み対策） |
| 情報の並べ方 | 横に広げるより**縦に積む** |
| カメラ映像上のレイヤー | light/dark 非依存の**ダーク固定**（`oncam-*` トークン）。`backdrop-filter` は使わない（低スペック機で GPU 合成コストが跳ねる） |
| disabled | **原則使わない**。押せない操作は DOM から取り除くか、押せるままにして理由を出す（→ 各画面の根拠節） |

> **`h-dvh` が必須である理由**: `min-h-dvh` は下限にすぎず高さを決めないため、下位に `min-h-0` を連鎖させても内側スクロール領域が高さを持てず、中身の量だけページ全体が縦に伸びる。AR 実行画面のコマンドパネルで顕在化し、#244 で `h-dvh` に修正済み。

## 3. navbar

### 3.1 レイアウト — 文脈スロットバー

**位置と高さは全画面で固定し、中身だけが変わる**。

```
┌───────────────────────────────────────────────────────────────┐
│ [左スロット]          [中央: ページ名]          [右スロット]      │ 72
│  min-w 208px           30px / 700              min-w 208px    │
│  Button md (56px)                              Button md (56px)│
└───────────────────────────────────────────────────────────────┘
   72px = Button md 56px + 上下 8px
```

### 3.2 画面別の中身

| 画面 | navbar | 左 | 中央 | 右 |
| --- | --- | --- | --- | --- |
| ホーム | あり 72px | `⬡ ProgPath`（非ボタン） | **めいろ** | `⬇ アプリをいれる` |
| 迷路作成・編集 | あり 72px | `← もどる`（保存ガード） | **めいろをつくる** / **なおす** | `✓ ほぞんして とじる` |
| **AR 実行** | **なし（没入）** | `← もどる` チップを画面左上に単独配置（56px・不透明） | — | — |
| ダウンロード | あり 72px | `← もどる` | **アプリを いれる** | 空 |

### 3.3 情報量

- **top bar 1 本のみ。** side rail / drawer / bottom nav / ハンバーガーは全て不採用。
- ナビゲーション項目は **最大 2 個**（ホーム / ダウンロード）。
- パンくずは置かない。

### 3.4 認知負荷上の根拠

- **同格の目的地が最大 2 つしかない。** Fluent Design は「5 個以下 → top nav」を指針とし、NN/g は「デスクトップで hidden navigation は発見率 27% vs 48〜50%、タスク完了が 39% 遅い」と報告している。隠す理由がない。
- **迷路編集・AR 実行を navbar のタブにしない。** これらはホームの子であってピアではない。タブにすると「保存していない編集中の迷路があるのに AR タブへ飛べる」状態が生まれる。
- **出口は画面ごとに 1 つ。** 「navbar のホームボタン」と「ページ内の戻る」が両方あると、2〜3 人で操作している状況で「押した人と違う経路で抜ける」事故が起きる。**成功指標の「全員が最低 1 回操作」は、誰が何を押したか全員が追える状態が前提**になる。
- **AR 実行だけ navbar を消す。** 3D の面積は中心価値そのもので、72px は 600px の 12%。ここを削るのは他画面での一貫性より優先する。代わりに `← もどる` を左上に単独で置き、**位置だけは navbar 左スロットと揃える**ので学習が転移する。
- **「戻」は教育漢字ではない** → 必ず `もどる` と表記する。

## 4. ホーム画面

### 4.1 レイアウト

```
1280 × 600
┌──────────────────────────────────────────────────────────────┐
│ ⬡ ProgPath            めいろ            ⬇ アプリをいれる       │ 72
├────────────────┬─────────────────────────────────────────────┤
│ 🎓 チュートリアル 3│ ＋ あたらしく つくる    📷 QR から よみこむ    │ 72
│ ────────────── │ ┌──────────────────┐ ┌──────────────────┐ │
│ 📁 じっけん     5│ │┌──────┐          │ │┌──────┐          │ │
│ 📁 きょうそう   2│ ││140×105│ めいろの ▶│ ││140×105│ めいろの ▶│ │ 137
│ ────────────── │ │└──────┘ 7×7 3かい│ │└──────┘ 7×7 3かい│ │
│ 📥 みぶんるい   7│ └──────────────────┘ └──────────────────┘ │
│                │ ┌──────────────────┐ ┌──────────────────┐ │
│ ＋ フォルダを   │ │                  │ │                  │ │ 137
│    つくる      │ └──────────────────┘ └──────────────────┘ │
│                │ ┌──────────────────┐  ← 3 行目は上端だけ見える │
│     256px      │ │      490px       │    （スクロールの合図）   │
└────────────────┴─────────────────────────────────────────────┘
```

**縦の予算**: `600 − 72(navbar) − 32(padding) − 72(アクション行) = 424px`
→ カード 137px + gap 12px = 149px 単位で **2 行が完全に見え、3 行目が見切れる**。

### 4.2 寸法

| 項目 | 値 | 導出 |
| --- | --- | --- |
| サイドバー | **256px** | アイコン 24 + gap 8 + フォルダ名 22px×7 文字(154) + gap 8 + 件数 30 + padding 32 |
| （↑の注意） | **〔要確認〕「…」の分が入っていない** | この導出は行末の「…」メニュー（タップ下限 48px）を勘定に入れていない。実測では 48px を差し引くとフォルダ名が全角 5 文字弱で切れ、既定選択の「チュートリアル」が「チュート…」になる。サイドバーを広げる／メニューを選択行だけに出す等の解決は #196 |
| コンテンツ領域 | 1024px | 1280 − 256 |
| カード | **490 × 137px**・2 列 | 幅 `(1024 − 32padding − 12gap) / 2`、高さ `105 + 16×2` |
| サムネイル | **140 × 105（4:3）** | Scratch ステージ 480×360 と同比。正方形だと縦に行数が入らない |
| カード内テキスト領域 | **234px** | 490 − 32(padding) − 140(サムネ) − 16(gap) − 56(▶) − 12(gap) |
| 迷路名 | 30px（主要ラベル）・**1 行 truncate** | 234px ÷ 30px ≒ **全角 7 文字** |
| サイズ・階層 | 22px（本文） | `7×7 3かい` |
| ▶ ボタン | **56px 円形・常時表示** | ホバー表示にしない |
| 詳細パネル | 右からスライドイン **360px** | 開くとカードは 1 列 × 660px に reflow |

> **迷路名が全角 7 文字で切れる。** 30px を優先した結果であり、長い名前は詳細パネルで全文表示する。実運用での平均名前長は未確認（→ 9.3）。

### 4.3 情報量

| 要素 | 個数 |
| --- | --- |
| サイドバーのセクション | **3**（🎓 チュートリアル / ユーザフォルダ群 / 📥 未分類） |
| 常時見えるアクション | **2**（あたらしく つくる / QR から よみこむ）+ フォルダ作成 1 |
| 完全に見えるカード | **4 件**（2 列 × 2 行）。見切れ込みで約 6 件 |
| カード 1 枚が持つ情報 | **4**（サムネ / 迷路名 / サイズ・階層 / ▶） |
| **置かないもの** | ソート・検索・表示切替・ページネーション |

- **カード本体クリック = 詳細パネルを開く**、**▶ = AR 実行に直行**。
- 起動時は **チュートリアルフォルダを選択済み**にする。→ AR まで **1 クリック**。

### 4.4 認知負荷上の根拠

- **ソート・検索・表示切替を実装しない**（更新日時降順で固定）。Scratch は 8〜16 歳向けで数百作品を持つユーザがいるのに**今もフォルダを持たない**。1 クラス分の迷路にソート UI は過剰で、選択肢そのものが負荷になる。
- **削除もリネームもできないフォルダ（= 未分類）に「…」メニューを DOM から出さない。** グレーアウトしない — **子どもは無効表示を読まず連打する**。区切り線 + アイコンの差 + 位置固定（先頭と末尾）で「これは特別」を伝える。判定は `entities/folder` の `canManageFolder` が持ち、`FolderItem` はメニューを渡されても描かない（消費側の実装ミスで穴が開かない）。
- **チュートリアル迷路は「編集」ではなく「コピーしてつくる」。** Minecraft の Re-Create、Figma の Duplicate と同型。これにより「なぜ編集できないのか」を説明する必要が消える。削除はできる（消しても戻る）ので説明が要らない。
- **▶ を常時表示にする**（ホバー表示にしない）。囲んでいる 2〜3 人のうちマウスを持っているのは 1 人だけなので、**ホバーは他の 2 人には存在しない状態**になる。「そこを押せ」と指差せることが協調の前提。
- 空状態は見出し + 1 文 + CTA 1 個。**〔要確認〕アプリ全体が空になりうる。** 以前は「チュートリアルが常在するので空にならない」としていたが、チュートリアルフォルダを削除可能にした（→ [features.md](./features.md) 3.4）結果、**未分類 1 つだけ・迷路 0 件**の状態が起こる。この状態の空表示と、チュートリアルを戻す導線（→ [features.md](./features.md) 3.6）の置き場所は #196 で設計する。

## 5. 迷路作成・編集画面

### 5.1 レイアウト

```
1280 × 600
┌──────────────────────────────────────────────────────────────┐
│ ← もどる    めいろをつくる  [名前___]   ✓ ほぞんして とじる      │ 72
├─────────┬─────────────────────────────────┬──────────────────┤
│ ゆか    │                                 │  ┌────┐ 3かい     │
│ かべ    │                                 │  │盤面│           │
│ あな    │     グリッド 493 × 493           │  ├────┤ 2かい     │
│ スタート │     （7×7 → 1 マス 67px）        │  │盤面│           │
│ ゴール  │     （6×6 → 79px / 5×5 → 96px） │  ├────┤ 1かい ●   │
│ うえへ  │                                 │  └────┘           │
│ したへ  │                                 │  [5×5][6×6][7×7]  │
│ カギ    │                                 │  ✓S ✓G ⚠テレポート │
│  192px  │            784px                │      240px        │
└─────────┴─────────────────────────────────┴──────────────────┘
```

**縦の予算**: `600 − 72(navbar) − 32(padding) = 496px`

### 5.2 寸法

| 項目 | 値 | 導出 |
| --- | --- | --- |
| パレット | **192px** | タイル 176px + padding 16 |
| パレットのタイル | **176 × 56px × 8 行**・gap **4px** | `8×56 + 7×4 = 476 ≤ 496` ✓ |
| 中央列 | 848px（内側 784px） | 1280 − 192 − 240 |
| **グリッド** | **493 × 493px** | `7×67 + 6×4` |
| 1 マス（7×7） | **67px** | `(496 − 4×6) / 7 = 67.4` |
| 1 マス（6×6） | **79px** | `(496 − 4×5) / 6 = 79.3` |
| 1 マス（5×5） | **96px** | `(496 − 4×4) / 5 = 96.0`（clamp 上限） |
| 右列 | **240px** | 階セレクタ + サイズ + チェックリスト |
| タイルラベル | 22px bold（ソリッド面のため） | → 2.2 |

- **セルは `clamp(48px, 計算値, 96px)`。** 上限を切らないと 5×5 が 99px になり 6×6（79px）との比が崩れて「小さい迷路のほうがマスが大きい」矛盾が視覚的に強く出る。
- **パレットの gap は 4px**（design-tokens §8 の「ターゲット間 8px 以上を推奨」の明示的な例外）。タイル自体が 56px あり WCAG 2.5.8 の 24px を大きく上回るため誤タップリスクは低く、8 種を 496px に収める制約を優先する。
- **エディタヘッダを navbar に統合するのは必須。** 別に持つと 1 マスが 67 → 59px に落ちる。

### 5.3 情報量

| 要素 | 個数 |
| --- | --- |
| パレットのタイル | **8**（ゆか / かべ / あな / スタート / ゴール / うえへ / したへ / カギ） |
| 階セレクタ | **最大 3**（縦積み・3F 上 / 1F 下・既定 1F） |
| サイズセレクタ | **3**（5×5 / 6×6 / 7×7） |
| 常設チェックリスト | **3**（✓ スタート / ✓ ゴール / ⚠ テレポート） |
| **置かないもの** | カテゴリタブ・検索・並べ替え・保存時モーダル |

### 5.4 認知負荷上の根拠

- **パレットは左サイド 1 列 × 8 行、並び順固定。** 8 種は前面定員（一度に見せてよい選択肢の上限）に収まるので、カテゴリ・検索・タブを作らない。位置が変わらないことが「あのタイルはあそこ」の記憶を成立させる。
- **階セレクタは縦積み + ミニ盤面サムネ、既定 1F。** 屋内地図の Floor selector の公式推奨（縦積み / 建物の縦順 / 5 個以内 / 地上階を既定）に完全一致する。
- **オニオンスキンはテレポート選択時に自動 ON**（隣接 1 階層のみ・25% グレー・上 = 寒色 / 下 = 暖色）。Revit のアンダーレイ（ハーフトーン灰色・上/下 2 方向・既存要素は二重に描かない）が 40 年来の定石。自動化することで**モード選択を子どもに一切させずに済む**。
- **エラーは「出させない」を最優先にする。**
  - スタート / ゴールはシングルトン（置く = 移動）。
  - 3 階で「うえへ」はパレット上でグレーアウト（**パレットは例外的に disabled 可** — DOM から消すと 8 行の位置が動き、位置記憶が壊れるため）。
  - サイズ縮小で範囲外に出たタイルは自動再配置する。
- **保存時モーダルを出さない。** 右列の常設チェックリストをライブ表示し、保存押下時は該当セルの強調パルス + 右列の展開 + `aria-live="assertive"`。**保存ボタンを disabled にしない**（押せないボタンだけでは児童が理由と対処に辿り着けない）。
- 文言は状態記述ではなく行動指示にする（「ゴールがありません」→ **「ゴールを おいてね」**）。

### 6.6 認知負荷上の根拠

- **命令列は縦。ネストがある言語で横並びを採る事例は、調べた範囲で存在しない。** Lightbot（PROC1/2）、Cargo-Bot（Prog1〜4）、RoboZZle（F1〜F5）はいずれも**別枠サブルーチンでネストという概念を UI から追放している**から横並びが成立する。ScratchJr が横並びなのは公式に「小画面向き」と明言されている。ProgPath は多重ループが確定仕様なので縦以外の選択肢がない。
- **画面上に命令パレットを再掲してはいけない。** Single Display Groupware（Stewart, Bederson & Druin 1999）の定義では**マウスとキーボードは同一の入力チャネル**（フォーカスを共有するため）と数える。**物理 QR カードは、カードの選択が画面のフォーカスに依存しないため、正真正銘の第 2 入力チャネル**であり、これが本アプリ最大の構造的アドバンテージ。画面にパレットを出すと「画面で選ぶ → カードを探す」の順序が生まれ、**チャネルが 1 本に戻る**。画面には"選ばれた結果"だけを出す。
  - 補強データ: Horn et al.（2009, CHI, n=260）は tangible 条件で「試す確率」「グループ内で能動的に参加する確率」が有意に高く、**特に女児で効果が強い**と報告。ただし「理解しやすさ」は両条件で同等 — 効くのは「同時に手を出せる」という具体的性質そのもの。
- **可視 6.4 件が最大のボトルネック。** 20 命令だと 3 画面ぶんスクロールする。→ 実行フェーズで下部の横ストリップに切り替える案（3D が +10.4%、可視が約 13 件）を**将来案として保持**し、#190 完成後に教室で実測してから判断する（→ 9.2）。
- **カメラ映像上では light/dark を諦める。** 背景の輝度が撮影環境で決まるため、テーマ追従させるとどちらかで必ず読めなくなる。`oncam-*` トークンでダーク固定にする。
- **`backdrop-filter` を使わない。** 低スペック機（Celeron / 4GB）で GPU 合成コストが跳ね、30fps 要件を割る。不透明な面で解決する。
- **QR の抑止は一律 2 秒を維持する。** 業界標準（Zebra / Honeywell の "remove & re-present" モデル）は同一コード 500ms / 別コード 100ms と細かく分けるが、本アプリは**「1 枚ずつ確実に読ませる」ことを優先**して一律にする（→ [features.md](./features.md) 5.3）。読み取りフィードバックのチップ寿命をこの 2 秒に揃え、**「消えた = 次を出していい」**という合図として機能させる。

- 赤いエラー色・`×` アイコン・警告三角を使わない（Tauri 状態は**エラーではない**）。
