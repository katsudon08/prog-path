# データモデル要件 (Data Models Requirements)

本ドキュメントでは、エンティティの構造、QRコードにエンコードされるデータの仕様、およびローカルデータベース（Dexie.js）のスキーマ方針を定義します。

## 1. コア・エンティティ
### 1.1. コマンド (Command)
シミュレーション上でロボットを動かすための命令単位。
- ロボットの動作は事前に定義されたリテラルとして扱う（`forward`, `right`, `left`, `if`, `loop`）。
- `if` や `loop` などの制御コマンドは、内部で実行する一連のコマンドを子要素として保つため、`children` プロパティ（Command型の配列）を持つ入れ子（ネスト）構造として定義される。

### 1.2. ロボット状態 (Robot State)
3D空間におけるロボットのステータス情報。
- 座標情報 (X, Y, Z: 階層)
- 方向 (Direction: 初期向きは常に「南向き(South)」で配置される)
- 現在のアニメーション状態 (Idle, Walking, Turning)

### 1.3. 迷路データ (Maze)
ロボットが走行するマップ（盤面）情報。
- **サイズ制約**: 1階層あたり最大「7×7マス」とし、縦に「最大3階層（3フロア）」の3次元配列データとして定義される。
- **マス目の種類**:
  床(floor), 壁(wall), スタート(start), ゴール(goal), テレポート(teleport: 上昇/下降), カギ(key) の全6種類。
- 児童が自ら作成したオリジナル迷路をQRコードに変換することで、他の児童がカメラで読み込み、作成された迷路をそのまま取り込んで遊ぶことができる（シェア機能の基盤データ）。

## 2. データシリアライズフォーマット (QRコード用)
QRコードのデータサイズ制約をクリアするためのエンコード仕様です。

- **コマンドデータ**:
  QRコード自体の容量設計は不要。1枚のカードには `forward`, `right`, `left`, `if`, `loop` のいずれかの単一の文字列のみがエンコードされている。フロントエンドがこれを検知し、複数回スキャンすることでアプリ内の状態としてスタック（ツリー）を組み上げる。
- **迷路データのプレフィックスとRLE**:
  読み取ったQRが迷路であることを識別するため、先頭に `M:` のプレフィックスを付ける。
  それに続くデータは、3次元配列データを一次元化し、続く同じ文字の数を圧縮するRLE (Run-Length Encoding) を行う。
  (例) `M:5A2B1A` (値に独自の文字アルファベットを割り振るなど)
  ※迷路データのQRコード化の最大の理由は、**児童同士が自分たちの作ったオリジナル迷路をQRでシェアし、お互いに読み込んで遊ぶため**である。
- **Base64化**: 必要に応じてURL SafeなBase64エンコードを施して出力する。

## 3. ローカルデータベーススキーマ (Dexie.js)
ユーザーの「進行状況」を失わないためのローカル永続化テーブル定義です。

- **`mazes` テーブル**: ユーザーが作成、または読み込んだ迷路データの履歴。
- **`commandHistories` テーブル**: 過去に成功または失敗したコマンドスタックの実行履歴。
