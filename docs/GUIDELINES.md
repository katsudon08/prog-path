# AR迷路アプリ 開発ガイドライン

本ドキュメントは、プロジェクト「prog-path」の品質、保守性、および一貫性を保つための開発ガイドラインを定義する。

---

## 1. ディレクトリ構成・アーキテクチャ

本プロジェクトでは **Feature-Sliced Design (FSD)** アーキテクチャを採用する。

### 🔘 採用理由
- **関心の分離**: レイヤーごとに役割を明確に分けることで、将来的にエディタ機能やステージ管理機能など複雑な機能が追加された際にも、コードベースが煩雑になるのを防ぐため。
- **再利用性の向上**: 依存関係が一方向に保たれる（上位レイヤーから下位レイヤーへのみ依存）ため、共通UIやドメインロジックを再利用しやすく、リファクタリングも安全に行えるため。
- **TDDとの親和性**: 各スライス（機能セット）が独立しているため、モック化やテストの粒度設計が行いやすい。

### 🔘 レイヤー構成（FSD標準準拠）
1. `app/` : アプリケーションの初期化、グローバルなプロバイダ設定、ルーティングのトップレベル。
2. `pages/` : ルーティングと対応する各ページの組み立て。
3. `widgets/` : 独立して機能するページ内の大きなブロック（例: `QrScannerWidget`, `MazeViewerWidget`）。
4. `features/` : ユーザーアクションによるビジネス価値を生む機能（例: `AddCommandBlock`, `RunProgram`）。
5. `entities/` : ドメインに紐づくデータモデル、UI、ロジック（例: `Maze`, `Robot`, `Command`）。
6. `shared/` : ドメインに依存しない共通のUIコンポーネント、ユーティリティ、APIクライアントなど。

*※下位（shared側）から上位（app側）をインポートしてはならない。*

## 2. テスト戦略 (Testing Trophy)

本プロジェクトでは **Testing Trophy**（統合テストを最も重視するテスト戦略）を採用し、以下の全レイヤーを自動化する。

1. **Static Analysis (静的解析)**
    - TypeScript, ESLintによる型チェックとルールの強制。
2. **Unit Tests (単体テスト)**
    - `entities/` などの純粋なドメインロジック、あるいはユーティリティ関数を中心にテストする。
    - ツール: Vitest
3. **Integration Tests (統合テスト) ★最重視**
    - コンポーネントツリーや、複数のHooks、ZustandのStoreが連携して正しく動作するかをテストする。
    - 原則として「内部の実装詳細」ではなく「ユーザーが見る振る舞い」をテストする。
    - ツール: React Testing Library + Vitest
4. **E2E Tests (End-to-End テスト)**
    - アプリ全体を通したクリティカルパス（カメラからQRを読み取り、ロボットがゴールするまで）をテストする。
    - ツール: Playwright または Cypress

*※今後、複雑なモックやテストデータの自動生成のために、MCP（Model Context Protocol）サーバーによる動的なプロキシ・モックサーバーの導入も検討する。*

## 3. 型安全性 (Strict Typing)

TypeScriptの機能を最大限に活用し、コンパイル時点でバグを防ぐ。

1. **厳格なコンパイラオプションの適用**
   - `tsconfig.json` において `strict: true` はもちろん、追加の厳格オプションを有効化する。
2. **`any` 型の完全禁止**
   - ESLintで `@typescript-eslint/no-explicit-any` を `error` に設定する。
   - 外部ライブラリの型が不明な場合は `unknown` を用い、型ガード（Type Guards）やZod等のバリデーションライブラリで安全にキャストする。
3. **型定義のコロケーション**
   - コンポーネントのProps等の型定義は、対象のファイル内、もしくは同階層の `types.ts` に配置する。

## 4. 開発プロセス: テスト駆動開発 (TDD)

品質のアジリティを保つため、**「テストコードファースト」**のTDDスタイルを徹底する。

### 🔘 実装フロー (Red-Green-Refactor)
1. **Red**: まず、達成したい振る舞い（要件）を満たすテストコード（Vitest / React Testing Library）を書く。（この時点では実装がないためテストは失敗する）
2. **Green**: テストを通過させるための最小限の実装（コンポーネントや関数）を書く。
3. **Refactor**: 実装が正しく動くことを担保した上で、コードをクリーンにリファクタリングし、FSDのレイヤー制約等に従って整理する。

### 🔘 AI（LLM）との協業フロー
1. 人間（ユーザー）が「〇〇という機能を作りたい」とAIに依頼する。
2. AIは要件から**テストケースを洗い出し、まずはテストコードのみを人間へ提示**する。
3. 人間はテスト内容をレビューする。
4. レビュー完了後、AIが「そのテストを通すためのプロダクトコード」を実装する。

### 🔘 AIの自律的なタスク管理・リポジトリ操作 (Git MCP Server)
本プロジェクトでは、プロジェクト管理やソースコードレビューの合理化のため、AIが**GitHub MCP (Model Context Protocol) サーバー**を通じてIssueやPull Request (PR) を自律的に操作することを許可・推奨する。

**運用手順とAIへの指示:**
1. **Issueの確認・作成**: 新たな機能要件やバグが発見された際、AIはMCPサーバーを通じて既存のIssueを検索し、存在しない場合は要件定義に基づいて新しいIssueを作成して人間（ユーザー）に報告する。
2. **ブランチの作成と作業**: AIは対象のIssueに基づき、適切な命名規則（例: `feat/issue-123-qr-scanner`, `fix/issue-45-bug`）でブランチを切って開発（TDD）を開始する。
3. **Pull Requestの自律的な作成**: 実装とテスト（Green状態）が完了したら、AIはMCPサーバーを用いて自律的にPull Requestを作成する。
    - PRのDescriptionには、対象Issueへのリンク（`Closes #123` 等）、変更の概要、および実行したテストの結果を明記する。
4. **レビューとマージ**: 人間がPRをレビューし、承認されたらマージする。修正が必要な場合はPR上でAIにフィードバックを行い、AIが追加コミットを行う。

## 5. UIコンポーネントカタログ (Storybook)

コンポーネントの再利用性とデザインの一貫性を保つため、**厳格なStorybookの運用**を行う。

- 対象: `shared/`（汎用コンポーネント）および `entities/`（ドメインUI）、必要に応じて `features/` のUIまでをドキュメント化する。
- Storybook駆動開発: 画面全体のロジックと結合する前に、コンポーネント単体の見た目と振る舞いをStorybook上で確認し、テスト（Interaction Test等）を記述する。
