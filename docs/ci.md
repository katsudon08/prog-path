## コミット前

### 使用技術

`lefthook`を使用しています。
Goで書かれているため高速で、Gitフックをより簡単にします。

参考記事：[Git フック管理ツール「Lefthook」の紹介](https://zenn.dev/sukesan0720/articles/87a8c005f82522)

### チェック項目

| 項目 | ツール | 実行されるコマンド |
| --- | --- | --- |
| フォーマット | Prettier | `npm run format -- <対象>` |
| 文法・コーディング規約 (コメントも含む) | ESLint | `npm run lint:fix -- <対象>` |
| ユニットテスト | 未定 | なし |
| コミットメッセージ規約 | commitlint | `npm run commitlint -- <メッセージファイル>` |

参考記事：[commitlint の紹介](https://qiita.com/ybiquitous/items/74225bc4bf0a9ddcd7dd)

**ユニットテストは意図的に未実装です。**
テストファイルが0件の状態で組み込んでも常に何も検査しないため、テストを書き始めるタイミングで導入します。

### 定義の置き場所

検査内容の定義は**すべて`package.json`のscriptsに集約**しており、`lefthook.yml`にはツールのオプションを一切書きません。

| ファイル | 責務 |
| --- | --- |
| `package.json` | **何を**検査するか（ツールのオプション） |
| `lefthook.yml` | **いつ・何に対して**走らせるか |

こうしておくと、フックと将来のGitHub Actionsで同じscriptを呼べるため、検査内容が二重管理になりません。

手元で使えるコマンドは次のとおりです。

| コマンド | 内容 |
| --- | --- |
| `npm run check` | **リポジトリ全体を検査する入口**。整形チェック→Lintの順に実行する |
| `npm run format -- .` | 全体を整形する |
| `npm run lint -- .` | 全体をLintする（修正はしない） |
| `npm run lint:fix -- .` | 全体をLintし、自動修正できるものは修正する |

検査対象をscriptに埋め込まず引数で受け取る形にしているため、`-- .`のように対象を渡す必要があります。
埋め込んでしまうと、lefthookからステージ済みファイルを渡したときに全ファイルが対象になってしまうためです。

### 実際の設定

```yaml
# 検査内容の定義は package.json の scripts に集約し、ここでは「いつ・何に対して走らせるか」だけを決める
pre-commit:
  commands:
    1_format:
      glob: "*.{ts,tsx,js,jsx,mjs,cjs,json}"
      run: npm run --silent format -- {staged_files}
      stage_fixed: true
    2_lint:
      glob: "*.{ts,tsx,js,jsx,mjs,cjs}"
      run: npm run --silent lint:fix -- {staged_files}
      stage_fixed: true

commit-msg:
  commands:
    commitlint:
      run: npm run --silent commitlint -- {1}
```

| 設定 | 意味 |
| --- | --- |
| `{staged_files}` | **ステージ済みのファイルのみ**を検査する。リポジトリ全体を毎回走査しない |
| `stage_fixed: true` | 自動修正の結果をステージに戻す。これがないと「整形されたのにコミットに含まれない」ズレが起きる |
| `1_` `2_` の接頭辞 | lefthookは名前順に実行するため、**整形→Lint**の順序を名前で固定している |

並列実行（`parallel: true`）は使用していません。
Prettierが書き換えている最中にESLintが同じファイルを読むと不整合が起きるためです。
実測でフック全体の所要時間は**1.1〜1.3秒**なので、並列化する必要がありません。

### 長文コメントの検知

チェック項目の「コメントも含む」に対応する設定です。
コメント1行が**60文字**を超えると警告が出ます。

```js
"@stylistic/max-len": ["warn", { code: 1000, comments: 60, ignoreUrls: true }]
```

| コメントの形 | 検知 |
| --- | :---: |
| `// 長い一行コメント` | ○ |
| `/* 長い一行ブロック */` | ○ |
| `/** */` の中の各行 | ○ |
| 行末コメント（`const a = 1; // ...`） | × |
| URLを含む行 | × |

`code: 1000`としてコードの行長を実質無制限にしているのは、コードの折り返しをPrettierの`printWidth: 100`が担当するためです。
ESLintが別途行長を検査すると二重管理になります。
行末コメントとURL行を対象外にしているのも同じ理由と、URLは折り返せないためです。

なお`max-len`は全角文字も1文字として数えるため、日本語60文字は表示幅で約120桁に相当します。

**日本語のコメントを自動で折り返す手段は存在しません。**
Prettierは仕様としてコメントの中身を変更せず、自動折り返しに対応するプラグインも日本語には対応していません（単語が空白で区切られないため）。
そのため検知のみを行い、修正は書いた人が行います。
`--max-warnings=0`によってコミットが停止するため、放置はされません。

## プッシュ前

**未実装です。**

### 使用技術

**コミット前**と同様に`lefthook`を使う想定です（`pre-push`フック）。

### チェック項目

| 項目 | ツール | 状態 |
| --- | --- | --- |
| 型チェック | TypeScript (`tsc --noEmit`) | 未実装 |
| インテグレーションテスト | 未定 | 未実装 |

型チェックをコミット前ではなくプッシュ前に置く理由は次の2点です。

- リポジトリ全体を走査するため時間がかかる
- **作業途中のコミットで型が通らないのは正常な状態**であり、そこで止めると作業の邪魔になる

導入時は`tsconfig.json`の`include`の調整が必要です。
現在は`**/*.ts`で全ファイルを拾っており、検査対象外にした`src/`も含まれてしまいます。

### 使用技術

`GitHub Actions`を用いてリポジトリにイベントが発生した際に、あらかじめ定義してワークフローを実行します。
イベントの種類としては多様ですが、今回のメインターゲットは**PR作成**のタイミングです。
また、CIのチェック項目はコミット前やプッシュ前にもチェックした項目を含めて包括的に行います。

参考記事：[(CI/CD)Github Workflows を使ってCI自動テストを作成](https://zenn.dev/hyoni/articles/d53a4c57979e7d)

### チェック項目

| 項目 | ツール | 状態 |
| --- | --- | --- |
| フォーマット | Prettier | 未実装（`npm run check`で実行できる） |
| 文法・コーディング規約 (コメントも含む) | ESLint | 未実装（`npm run check`で実行できる） |
| 型チェック | TypeScript | 未実装 |
| ユニットテスト | 未定 | 未実装 |
| インテグレーションテスト | 未定 | 未実装 |

| ビルド | Next.js (`npm run build`) | 未実装 |

フォーマットと文法・コーディング規約については`npm run check`がそのまま使えます。
コミット前と同じscriptを呼ぶため、検査内容がずれることはありません。

### なぜコミット前と重複して検査するのか

ローカルのフックは`git commit --no-verify`で外せます。
外せるものを品質の根拠にはできないため、**CIでは前段と同じ検査をすべてやり直します**。
重複は無駄ではなく、早い段階で気付くための対価です。
