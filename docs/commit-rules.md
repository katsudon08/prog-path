## このドキュメントの概要

Gitにおけるコミットメッセージを一定の書式に統一することを目的に規約の概要を記述しています。
人間とAIの両方が何をしたコミットなのかを端的に理解できるようにするための規約です。
参考にした記事の中では、Gitフックの役割として`Husky`を採用していますが、本リポジトリにおいては`lefthook`を採用しています。

参考記事：[Conventional Commits の基礎知識とそれを支える技術（commitlint + husky）](https://zenn.dev/wakamsha/articles/about-conventional-commits)

## 対象読者

手動かAIでコミットメッセージを作成するエンジニアを対象としています。
基本的にはコミット前の`lefthook`でのチェックにより、このドキュメントに記されている形式である`conventional commits`の形を満たしていないコミットに関しては弾かれるように設定されています。

## 書式 (`Conventional Commits`)

> Conventional Commits とは、Git などにおけるコミットメッセージを一定の書式に統一することを目的とした規約です。人間と機械のどちらも理解しやすいように設計されており、端的でありながら明瞭なコミットメッセージを記述できます。これにより後からコードベースの変遷を追跡しやすくなるだけでなく、リリースワークフローやコードレビューを自動化するツールとの連携も容易になります。

基本的な書式としては以下の形で記述します。
公式では`subject`や`body`は英語での記述ですが、本リポジトリにおいては日本語で記述することとします。

```text
<type>(<optional scope>): <subject>
<BLANK LINE>
<body>
<BLANK LINE>
<footer>
```

記述例

```text
feat: 機能の追加
fix(api): バグの修正
```

## type一覧

公式が定義しているtypeは全てで以下の10種類です。

- fix: バグの修正パッチ
- feat: 新機能の追加
- docs: ドキュメントの変更
- style: コードのスタイルの変更（セミコロンの追加や改行の修正など）
- refactor: コードのリファクタリング（バグの修正や機能の追加は含まない）
- perf: パフォーマンスの向上
- test: テストの追加・修正
- build: ビルドシステムの変更または依存関係のアップデート
- ci: CI/CD の設定の変更
- chore: その他の変更
